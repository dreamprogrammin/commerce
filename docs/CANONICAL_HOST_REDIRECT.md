# Канонический хост: почему всё, кроме `uhti.kz`, редиректит

Правило живёт в `vercel.json`, первым в массиве `redirects`. JSON комментариев
не держит, поэтому объяснение здесь — как и для соседнего правила про
`?brand=`, которое описано в `server/middleware/brand-query-redirect.ts`.

```json
{
  "source": "/:path*",
  "has": [{ "type": "host", "value": "^.*\\.vercel\\.app$" }],
  "destination": "https://uhti.kz/:path*",
  "permanent": true
}
```

## Что оно чинит

Деплои Vercel доступны не только по `uhti.kz`, но и по собственным адресам.
Найдено 21 августа 2026 — не догадкой, а через диагностику тега Google
Analytics: она сама перечислила домены, с которых прилетают события.

Проверка показала, что это **полные, открытые к индексации копии магазина**:

```
commerce-eta-wheat.vercel.app          200 | robots.txt indexable, Allow: /
                                           | x-robots-tag: index, follow, max-image-preview:large…
                                           | счётчик G-7FZ401T438 — тот же, что на боевом
commerce-8e2o0m9ne-…vercel.app         200 | то же самое, но сборка постарше
```

`commerce-eta-wheat.vercel.app` — постоянный адрес проекта, он всегда смотрит
на текущий прод. То есть это не эфемерная ссылка, а вторая копия сайта,
живущая рядом сколько угодно долго.

Вреда три, по убыванию:

1. **Дубль всего магазина** — 300+ страниц по второму адресу. `canonical`
   везде указывал на `uhti.kz` и, судя по всему, склейку и обеспечивал, но
   canonical это подсказка, а не запрет.
2. **Краул-бюджет** — робот качает копию целиком, чтобы затем выбросить.
3. **Статистика** — заходы на копию шли в тот же счётчик GA4 и подмешивались
   к боевым цифрам.

## Почему правило В `vercel.json`, а не в серверном ПО Nitro

Двумя причинами, и обе жёсткие.

**Первая: до серверного ПО запрос может не дойти.** Правило
`'/catalog/**': { isr: 1800 }` заворачивает запрос в ISR-функцию раньше. Это
уже описано в `server/middleware/brand-query-redirect.ts` — там из-за этого
не работал редирект со старых бренд-адресов.

**Вторая, и она страшнее: кеш ISR ключуется ПУТЁМ, а не хостом.** Ответ,
собранный для одного хоста, отдаётся другому. Редирект, зависящий от хоста и
сделанный внутри функции, попал бы в кеш — и посетители `uhti.kz` получали бы
редирект на `uhti.kz`, то есть петлю. Правило платформы срабатывает ДО
маршрутизации функций и до кеша, поэтому такой ошибки не даёт.

Локального двойника у этого правила намеренно НЕТ. У соседнего,
`?brand=`-редиректа, он есть — ради `pnpm dev`, где `vercel.json` не читается.
Здесь такой двойник был бы вреден: локально хост это `localhost:3000`, и
редирект уводил бы разработчика на боевой сайт с первой же страницы.

## Что этим сломано, осознанно

**Прямые адреса деплоев больше не открываются — ни прод, ни превью.** Регулярка
ловит любой `*.vercel.app`.

`dev.uhti.kz` НЕ задет: это отдельный домен, под шаблон он не подходит, и
проверка превью работает как раньше.

Цена в том, что в HANDOFF записан приём «проверять по прямому адресу деплоя, а
не только по `dev.uhti.kz`: алиас переключается не мгновенно». Этот приём
теперь недоступен. Если он понадобится — правило временно убирается, и это
осознанный размен: постоянная дыра в индексации против редкого удобства.

## Как проверить, что работает

Локально проверить нельзя: `vercel.json` читает только платформа. После
выкатки:

```bash
curl -sS -o /dev/null -w '%{http_code} → %{redirect_url}\n' https://commerce-eta-wheat.vercel.app/
# ожидается: 301 → https://uhti.kz/

curl -sS -o /dev/null -w '%{http_code}\n' https://uhti.kz/
# ожидается: 200, петли нет

curl -sS -o /dev/null -w '%{http_code}\n' https://dev.uhti.kz/
# ожидается: 200, превью не задето
```

Отдельно стоит проверить путь с параметрами: платформа переносит исходную
query-строку в цель сама, так что `…vercel.app/catalog/boys?sort_by=price_asc`
обязан прийти на `uhti.kz` вместе с параметром.
