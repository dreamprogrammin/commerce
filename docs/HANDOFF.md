**Метод оказался негодным, и это надо знать.** Я гасил предзагрузку перехватом

**Что остаётся настоящим дефектом:** `/catalog/all/_payload.json` качается
**семь раз** (107 КБ впустую). На главной семь ссылок на `/catalog/all`, и
каждый `NuxtLink` предзагружает сам по себе. Вот это стоит чинить — в отличие
от отключения предзагрузки целиком.

Управляется `experimental.defaults.nuxtLink`, умолчание Nuxt —
`{ prefetch: true, prefetchOn: { visibility: true } }`; альтернатива
`prefetchOn: { interaction: true }` — наведение и фокус (`nuxt-link.js:273`).

### 26 августа: рывок персональных блоков на главной (в `dev`, не выкачено)

Владелец: «когда пользователь залогинен, мы ему предлагаем товары, которые
подобрали; когда он скролит, у него внезапно он появляется — впечатление
резкости».

Разобрано на две независимые причины, обе починены в `fix/home-personal-block-jank`.

**Причина 1 — карточка активного заказа выталкивала страницу.** Она живёт в
`ClientOnly` (SSR-разметка главной общая и лежит в ISR-кеше, персонального в ней
быть не может), поэтому блок вырастал из нуля уже после гидрации и толкал вниз
всё, что ниже, включая ленту.

Замер на стенде (390px, Slow 4G, CPU ×4, h2-proxy) до правки:

```
CLS залогиненного   0.0479      против 0.0058 у гостя
из них один сдвиг   0.042 на 9108 мс — блок над лентой 32 → 160px
лента                486px, 10 карточек — сама не меняется, её просто сдвигало
```

**Опровергнуто по дороге:** я сперва сказал, что чинить надо старт запроса —
между DCL 4984 мс и уходом запроса 7922 мс зияли три секунды. Неверно. Без
троттлинга разрыв всего полсекунды (гидрация 719 мс, карточка 1228 мс), сам
ответ приходит за 182 мс. Эти три секунды — стоимость гидрации под CPU ×4, и
раньше неё запрос не уйдёт ничем. Ускорять было нечего, надо было резервировать.

Решение: компонент измеряет отрисованную карточку и кладёт высоту в
`localStorage` (`uhti:active-order-height`, TTL неделя), а инлайн-скрипт в
`<head>` главной читает её **до первой отрисовки** и ставит
`--active-order-reserve` на `<html>`. `.active-order-slot` держит `min-height`.
Ни у гостя, ни у того, у кого активного заказа нет, подсказки нет — резерв
нулевой. Пока данные едут, место занимает скелетон, повторяющий карточку
(проверено снимками: 112px и там, и там).

Высоту считать из отступов нельзя — строка статуса переносится по-разному;
поэтому она именно измеряется. Подсказку снимает сам компонент, когда активного
заказа не нашлось, а у гостя и у админа (там `ActiveOrderStatus` не монтируется
вовсе) — watcher на странице.

**Причина 2 — лента менялась под рукой.** Секция «Подобрали для вас» стоит на
одном месте: в SSR там новинки, у залогиненного её подменяют рекомендации,
приезжающие отдельным запросом. Высоту секция не меняет, то есть **в CLS этого
не видно вовсе** — только глазами.

Теперь подмена запрещена, только если человек уже листал страницу И лента в этот
момент на экране. Правило намеренно узкое — рекомендации это деньги. Проверено
`feed-swap-check.mjs` (различает ленты по ссылке «смотреть все»):

```
не листал (обычный путь)     → персональная
стоит на ленте               → новинки, подмены нет
пролистал ленту вниз         → персональная
```

Первая версия правила («меняем, только если лента ниже экрана») была слишком
грубой: на 390×844 лента начинается на 691px, то есть видна сразу, и
рекомендации не показались бы никогда. В коде осталось узкое правило.

**Итог замеров на том же стенде:**

```
                                было      стало
залогиненный, повторный визит   0.0479    0.0021   сдвига на 9 с нет
залогиненный, первый визит      0.0479    0.0427   подсказки ещё нет
десктоп 1280                    0.03      0.0108
гость                           0.0058    0.0058   слот 0px, дыры нет
```

**Что осталось и почему не чинится:** первый в жизни визит залогиненного всё
ещё сдвигается один раз — SSR-разметка общая, знать про заказ она не может.
Визит сразу после закрытия заказа один раз схлопывает резерв, после чего
подсказка снимается. Оба случая разовые.

Инструменты замера лежат в корне: `cls-logged-in.mjs` (два прогона в одном
контексте — холодный и повторный), `feed-swap-check.mjs`.

**Линтер:** базовый уровень `ActiveOrderStatus.vue` — 10 ошибок
`ts/no-use-before-define` на `displayOrder`, они предсуществующие. После правки
ровно те же 10, новых нет.

### 26 августа, продолжение: «Ваше избранное» (в `dev`, не выкачено)

Владелец: «ваше избранное приходит с рывком на мобилке». Отдельная секция, но
причина той же природы, что и у карточки заказа, — и потому механизм резерва
обобщён на обе.

**Почему это не поймалось предыдущим замером.** Две вещи сразу:

1. У тестового пользователя локально было **пустое избранное** — секция просто
   не рисовалась. Пришлось засеять: `insert into wishlist ... limit 6` для
   `653f339a-250a-4e52-ba86-6adcaf6fbfa5`. Строки в локальной базе оставлены,
   без них воспроизведения нет.
2. Даже с непустым избранным **CLS этого не видит**. Вставка происходит ниже
   экрана, а сдвиги за пределами вьюпорта в метрику не попадают. По CLS страница
   была чистая, рывок был виден только глазами при скролле.

Отсюда правило: **для секций ниже первого экрана мерить положением, а не CLS.**
Инструмент — `sections-timeline.mjs` (снимает y всех заголовков внутри
`.home-content` каждые 250 мс; флаг `--warm` делает прогревочный визит, чтобы
подсказки о высоте успели записаться).

**Что было, замер на стенде 390px / Slow 4G / CPU ×4:**

```
 8190 мс   страница 7392px   «Подобрали для вас» y=839    «Популярные категории» y=1337
11095 мс   страница 7910px   «Ваше избранное»   y=839
                             «Подобрали для вас» y=1357   «Популярные категории» y=1855
```

Разом +518px — вчетверо больше карточки заказа.

**Что стало (повторный визит):** секции стоят на конечных местах с первого
снимка, «Подобрали» 1357 и «Категории» 1855 не двигаются вовсе. CLS 0.0021 →
0.0017. Гость — 0.0058 без изменений, оба слота 0px, подсказки нет. Когда
избранное опустело, ключ `wishlist` снимается, `order` остаётся.

**Первый визит был стал хуже по цифре: CLS 0.0427 → 0.0842 — артефакт метрики,
а не регресс.** Геометрия до и после совпадала до пикселя (страница 7392 → 7910,
те же y). Раньше сдвиг не считался, потому что двигавшийся элемент уничтожался и
создавался заново: серверная лента исчезала, а на её месте появлялась другая.
Когда лента осталась на месте, а секция стала расти над ней, тот же самый сдвиг
наконец попал в метрику.

**Закрыто следующей веткой** — см. ниже, владелец решил переставить секцию под
ленту.

**Грабли, стоившие времени:**

- Высоту избранного нельзя снимать разово на `nextTick`: карусель ленивая, её
  чанк в этот момент ещё грузится, `offsetHeight` равен нулю — подсказка молча
  не записывалась. Сейчас там `ResizeObserver`.
- Наблюдатель висит на внутренней обёртке, а не на самом слоте: у слота есть
  `min-height`, и измерение слота переписывало бы подсказку ей же самой.
- **Зелёная сборка не значит, что страница жива.** Перестановка блоков в
  `<script setup>` съела объявление `showRecommendedCarousel`; `pnpm build`
  прошёл без единой ошибки (шаблон компилируется против рантайм-скоупа), а SSR
  падал с 500 на каждом запросе. Прод-сборка текст ошибки прячет — видно только
  в `pnpm dev`: `curl` отдаёт JSON с `message` и стеком. **После каждой сборки
  дёргать главную и сверять код ответа**, это одна команда.

Механизм резерва теперь в `composables/home/useHomeReserve.ts`: обе высоты под
одним ключом `uhti:home-reserve`, инлайн-скрипт ставит из них переменные
`--active-order-reserve` и `--wishlist-reserve`. Проверки:
`sections-timeline.mjs --warm`, `cls-logged-in.mjs`, `verify-reserve.mjs`,
`feed-swap-check.mjs`.

#### «Акции и бонусы» росли на 854px — починено, выкачено

Блок рос на мобилке **373 → 1039 → 1285px**. Две причины:

1. На весь блок стоял `Skeleton h-64` — 256px там, где содержимое занимает 922.
2. Карточка дня брала товар в `onMounted` обычной публичной выборкой
   `is_featured` — это и был второй скачок, +246 на 7372 мс.

Разделение по признаку «персональное или нет»: карточка дня и плитки —
публичные, вынесены из `ClientOnly` и рисуются на сервере. Баннер лояльности
остался клиентским и получил третью часть резерва (`loyalty`).

**Почему баннер нельзя отдать серверу:** у гостя он 644px, у залогиненного 586 —
на 390px кнопки у гостя переносятся на вторую строку. Кнопкам не хватает **21px**
до одной строки (доступно 306, нужно 327 с зазором); подгонять дизайн ради
этого не стал, решение не моё.

Прокрутки нет ни в одном столбце. Googlebot её и не делает — он рисует

### Регрессия от неразрывных пробелов — найдена и починена 26 августа

**Что было сломано.** Итоговая сумма в липкой панели корзины и в карточке
товара рисуется анимированным барабаном цифр. Он разбирает строку от
`formatPrice` посимвольно, и проверка была такая:

```js
const isDigit = !Number.isNaN(Number(char)) && char !== ' '   // U+0020
```

`Number('\u00A0')` равен 0, а не NaN — неразрывный пробел для JS такой же
пробельный символ, как обычный. Поэтому после перехода `formatPrice` на
U+00A0 разделитель разрядов стал считаться ЦИФРОЙ, и барабан рисовал лишний
столбец: «31 170 ₸» превращалось в «311700₸». Проверено числом: на проде
12 барабанов на ту же корзину, после правки 10 (пять цифр × два счётчика).

**Где было:** `pages/cart.vue` (строки 92, 715, 797) и
`pages/catalog/products/[slug].vue` (279, 1236).

**Как починено:** `isDigit` теперь `/\d/.test(char)`, а пробелы в шаблонах
рисуются по `!isDigit`, а не сравнением с конкретным символом. От вида пробела
не зависит вовсе.

**Урок на будущее:** правка `formatPrice` задевает не только вёрстку. Он
используется в 119 местах, и часть из них РАЗБИРАЕТ его вывод, а не просто
выводит. Перед такими правками проверять корзину и карточку товара глазами —
через гостевой сценарий, логин для этого не нужен.

### Корень всей платы — картинки, а не разметка

Это главный вывод сессии, и он не был очевиден. Ни объём DOM, ни гидрация к
делу не относятся. Проверено прямо: заблокируешь картинки — DCL ветки падает
с 8389 до 3695 мс, то есть почти до уровня `master`.

Механика: секция в SSR-разметке означает, что браузер находит её картинки
сразу и тянет их наперегонки со скриптами. У `master` до DOMContentLoaded
успевает ОДНА картинка (герой, 53 КБ), у `dev` — все, что попали в разметку.

Отсюда правило, которого в проекте не хватало: **`sizes` объявлять по
фактической ширине КАРТИНКИ, а не контейнера.** У плиток категорий при
`layout="corner"` картинка занимает 132px в плитке 150px, и на экране с DPR 3
это 396px против порога варианта `sm` в 400px. Объяви 150px — браузер возьмёт
`md` на 800px, впятеро тяжелее. Размеры снимать в браузере через
`getBoundingClientRect()`, а не прикидывать по вёрстке.

Что проверено и НЕ помогает, повторять не надо:

- **отложенная гидрация** (`hydrate-on-visible` на всех четырёх секциях) —
  DCL 8432 → 8467 мс, то есть ничего;
- **`fetchpriority="low"` на карточках** — 8467 против 8432, ничего (но
  замерено на h1-стенде, на H2 не перепроверено);
- **урезание объёмов** (лента 10 → 6, хиты 8 → 4) — по товарным картинкам
  ноль: до DCL успевают одни и те же пять, остальные ниже сгиба или за краем
  карусели. Отброшено. Логотипы брендов — единственное, что резать стоило.

Отброшенные правки лежат в `git stash` (`WIP on perf/home-lazy-hydration`) —
не удалял, но и возвращать незачем, все три опровергнуты замером.

### Открытое решение владельца

Остаточная плата — FCP и LCP около +0.3 с, DCL около +2.5–3.5 с.

**Следующий рычаг, и он самый крупный: промежуточного варианта картинки нет.**
Из 419 КБ, уходящих до DCL, 289 КБ — это пять товарных карточек ленты по 58 КБ
каждая, вариант `md` на 800px. Карточке при DPR 3 нужно около 540px. В
`config/images.ts` есть только `sm` 400px и `md` 800px, промежуточного нет —
браузер вынужден брать вдвое больший. Добавить вариант на ~560px значит
править конвейер картинок и перегенерировать существующие, это не строчка в
коде. Решение владельца.

Если плата неприемлема прямо сейчас, второй путь — вернуть «Хиты продаж» и
«Популярные бренды» на клиент, оставив в SSR только ленту и категории. Ленту
оставлять обязательно: она вверху страницы и даёт −2.4 с. Откатывается легко,
весь SSR секций живёт в `pages/index.vue` и трёх компонентах
`components/home/`.

### CLS от подмены шрифта — разобран 25 августа, оставлен как есть

CLS главной 0.0058 против 0.0017 у `master`. Правки его не создали, а
обнажили: с заблокированными шрифтами он падает до 0.00007. Заголовок
«Подобрали для вас» на 390px переливается с двух строк на одну — H2 теряет
28px, лента подтягивается на 20px. Раньше карусель появлялась на 7.8 с, когда
шрифт давно загружен, и переливаться было нечему.

**Чинить нечем, и это проверено, а не предположено.** Разобрано полностью:

- **Метрические запасные грани уже работают.** `@nuxt/fonts` сам создаёт
  `Nunito Fallback: Arial` и прочие с `size-adjust` и сам подставляет их в
  `--font-sans` — без всякой настройки. Моя первая гипотеза («переменная на
  них не ссылается, нужен `experimental.processCSSVariables`») оказалась
  неверной: фолбэки в переменной есть и без флага.
- **`size-adjust` этот сдвиг не лечит в принципе.** Он выравнивает
  вертикальные метрики, а не ширину символов, а перенос строки зависит именно
  от ширины. Замерено в браузере: настоящий Nunito даёт 182px на «Подобрали
  для вас», подогнанная грань поверх Roboto — **221px**, то есть на 21%
  ШИРЕ оригинала. Хуже, чем неподогнанный запасной (218px).
- **Добавление Roboto в список запасных ничего не даёт.** Проверено с
  настоящей установкой Roboto в систему: CLS 0.00578 и с ним, и без него,
  до единицы. (В списке по умолчанию Android-шрифта нет — но пользы от него
  не оказалось, поэтому и добавлять нечего.)
- **Предзагрузить шрифт нельзя дёшево.** Тегов `<link rel="preload"
  as="font">` в разметке ноль. Ключ `preload: true` стоял в корне `fonts` —
  модуль его не читает вовсе (`shouldPreload` смотрит на `defaults.preload` и
  `families[].preload`); ключ убран и заменён комментарием. Перенести его в
  `defaults` значит предзагрузить все грани — у одного Nunito их 18.
- Остаются варианты с видимой ценой: `font-display: optional` (первый визит
  целиком на запасном шрифте) или запрет переноса заголовка (многоточие на
  2 секунды). Оба хуже, чем 0.0058 при пороге 0.1.

**Важная оговорка про сам замер.** В этом контейнере НЕТ ни одного из пяти
запасных шрифтов: `local(Arial)`, `local(Noto Sans)` и остальные не находят
ничего (`fc-list` знает только Nimbus Sans и DejaVu Sans), браузер
проваливается на DejaVu — он заметно шире. На реальном устройстве подставится
своё: iOS — San Francisco, Windows — Segoe UI. Так что 0.0058 это лабораторное
число конкретно этой машины. **Правда — в полевых данных**: сайт собирает CLS
с живых посетителей, и в записи от 21 августа поле по главной было 0.0020.
Смотреть надо туда, а не в лабораторию.

### Шрифты: 106 КБ уходило на два символа — закрыто 25 августа

На главной скачивалось 188 КБ шрифтов, из них **106 КБ — несокращённые
легаси-`.woff` по 52 КБ**. Причина оказалась не в числе начертаний, а в двух
символах видимого текста, которых нет ни в одном подключённом подмножестве:

```
₸  U+20B8, 43 раза  — живёт в latin-ext, а подключены были cyrillic и latin
→  U+2192, 1 раз    — в «Смотреть все &rarr;»; у Google в latin есть ↑ и ↓,
                      а → нет
```

**Правило, которое стоит помнить:** любой непокрытый символ в ВИДИМОМ тексте
заставляет браузер взять грань, которая его покрывает, а покрывают только
полные легаси-грани — и он тянет их целиком. Один символ стоит 52 КБ на
каждый вес, которым он набран.

Обе правки нужны вместе, поодиночке не дают ничего: убрал стрелку — остался ₸
и те же 106 КБ; добавил `latin-ext` — осталась стрелка и стало 158 КБ.

Итог: 188 → 117 КБ, легаси-загрузок ноль.

**Как искать такие символы.** Пройти по видимому тексту (исключая `SCRIPT`,
`STYLE`, `NOSCRIPT`) и сверить каждый код-пойнт с `unicode-range` всех граней
семейства из `document.styleSheets`. Скрипт разовый, но приём записан здесь:
без него легко искать причину не там — я успел обвинить и число весов, и
эмодзи (они лежат в JSON-LD внутри `<script>` и на выбор шрифта не влияют).

Проверено и отброшено, повторять не надо:

- **своя грань только под ₸ (1.2 КБ вместо 34.8 КБ подмножества).** Идея
  верная — Google по `css2?family=Nunito:wght@400..900&text=₸` отдаёт файл на
  1236 байт, покрывающий все веса, — но @nuxt/fonts не даёт её применить.
  Три подхода, все проверены сборкой 25 августа:
  1. **Отдельное семейство первым в стеке** (`'Nunito Tenge', 'Nunito', …`).
     Модуль ищет шрифты, разбирая `font-family`; увидев первым семейство с
     собственной @font-face, он считает объявление обслуженным и до `Nunito`
     не доходит — в сборке НОЛЬ его граней, сайт рисуется системным шрифтом.
     Объявление `{ name: 'Nunito' }` в `families` не помогает: этот список
     настраивает найденные шрифты, а не заставляет искать.
  2. **Та же грань внутри семейства `Nunito`** в `assets/css/tailwind.css` —
     модуль перестаёт генерировать грани для семейства, у которого уже есть
     собственная @font-face. Снова ноль.
  3. **Грань в `app.head.style`**, вне обрабатываемого CSS. Модуль её не
     видит и грани генерирует (18 штук), но стиль в head встаёт ДО ссылок на
     CSS модуля (позиция 594 против 769), то есть проигрывает его
     несокращённым граням: легаси-`.woff` вернулись, 188 КБ вместо 117.
     Заодно: ключ `children` у `app.head.style` рендерится АТРИБУТОМ тега, а
     не содержимым — в Nuxt 4 нужен `innerHTML`.

  4. **Vite-плагин, вырезающий легаси-грани из готового CSS** и дописывающий
     свою грань под ₸ — то есть ровно то, чего не хватало в подходах 1–3.
     Технически сработало: в сборке осталось 12 подмножеств woff2 плюс наша
     грань, легаси-граней ноль, шрифты 117 → 84 КБ на главной и 93 → 60 КБ на
     категории. **Но сломалось жирное начертание.** Замер 25 августа: строка
     «7 390 ₸» на весе 700 и 800 стала 70px против 60px, то есть браузер
     синтезирует полужирный вместо настоящего. Веса 700/800/900 остаются
     `unloaded` даже после `document.fonts.load()`, при том что файлы
     отвечают 200 и все веса ссылаются на одни и те же два woff2. Механизм
     остался непонятым, поэтому откачено: 33 КБ не стоят кривого жирного на
     каждой цене и заголовке.

  Чтобы это сработало, нужна возможность запретить модулю генерировать
  несокращённые легаси-грани (у него нет опции `formats`) либо объявить свою
  грань ПОСЛЕ его CSS **без потери настоящих начертаний**. Ни того, ни другого
  в 0.12.1 нет. Оставлено на `latin-ext`: 34.8 КБ ради одного глифа, зато
  предсказуемо, без легаси и с правильным жирным.

- **вариативный шрифт** (`weights: ['400 900']` вместо перечисления). У Google
  это 58 КБ против 351 КБ, но в сборке стало ХУЖЕ — 241 КБ против 188:
  легаси-грани качались всё равно, а вариативные добавились сверху. При
  перечислении Google и так отдаёт один файл на все веса, модуль его
  дедуплицирует, так что выигрыша там нет вовсе.
- **начертания резать не нужно.** Используются 400/500/600/700/800 (900 —
  шесть раз на весь проект), и стоят они столько же, сколько одно.

### ЖДЁТ ДОСТУПА: стрелки и 🔥 в генераторе FAQ

Тексты `category_questions` пишет функция `generate_category_questions` в

### Найдено инспекцией и починено: бренд-страницы были пусты для робота

на странице (`useBrandPageSsrProducts`), композабл остаётся синхронным.

**Две ловушки, обе стоили по сборке:**

- **`setQueryData` недостаточно.** В `useBrandPageFilters` ниже стоят два

  оставалась со скелетоном и «0 товара». Лечится `initialData`.
- **В префетче обязателен `categorySlug: 'all'`.** RPC
  `get_filtered_products` объявлен с `p_category_slug`, и без него PostgREST
  отвечает `PGRST202` «функция не найдена» — запрос падает целиком, а не
  возвращает пустой список. Клиентский путь это значение подставляет, поэтому
  на клиенте всё работало и дефект был невидим.

Пустые линейки закрыты `noindex` — по данным префетча, а не по
`filterState.products`: тот на сервере пуст и закрыл бы все линейки подряд.

```js
import { createSign } from 'node:crypto'
import { readFileSync } from 'node:fs'

const sa = JSON.parse(readFileSync('service-account.json', 'utf8'))
const now = Math.floor(Date.now() / 1000)
const b64 = o => Buffer.from(JSON.stringify(o)).toString('base64url')
const unsigned = `${b64({ alg: 'RS256', typ: 'JWT' })}.${b64({
  iss: sa.client_email,
  scope: 'https://www.googleapis.com/auth/webmasters.readonly',
  aud: 'https://oauth2.googleapis.com/token',
  exp: now + 3600,
  iat: now,
})}`
const sig = createSign('RSA-SHA256').update(unsigned).sign(sa.private_key, 'base64url')
const { access_token } = await (await fetch('https://oauth2.googleapis.com/token', {
  method: 'POST',
  headers: { 'content-type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({
    grant_type: 'urn:ietf:params:oauth:grant-type:jwt-bearer',
    assertion: `${unsigned}.${sig}`,
  }),
})).json()

// дальше — POST на
// https://searchconsole.googleapis.com/v1/urlInspection/index:inspect
// { inspectionUrl, siteUrl: 'sc-domain:uhti.kz' }
// смотреть inspectionResult.indexStatusResult.{verdict,coverageState}
```

Скрипт класть в корень репозитория и удалять после работы.

**Чем проверять при следующем касании:** число карточек в SSR против числа
активных товаров бренда в базе. Совпадать должно точно. Заголовок и H1
показываются правильно даже когда сетка пуста — глазами не видно.

### Что стоит запомнить из этих правок

**CLS бренд-страниц чинился не тем, чем казалось.** Виноват был не «поздний
блок отзывов» (эта версия из записи за 19 августа неверна), а блок
«Коллекции»: `brandProductLines` был обычным `ref`, наполняемым из
`watchEffect`, поэтому в серверной разметке блока не было ВОВСЕ, и его
вставка на третьей секунде толкала сетку на 171 px. Это ровно то правило из
CLAUDE.md про `useAsyncData`, который обязан ВОЗВРАЩАТЬ данные. Побочно
закрылась дыра во внутренних ссылках: ссылки на страницы линеек теперь есть
в SSR.

**Рассинхрон гидратации — это `reka-ui`, и он НЕ починен.** Диагноз снят с
прод-сборки, собранной с `__VUE_PROD_HYDRATION_MISMATCH_DETAILS__`: сервер
отдаёт `reka-popover-trigger-v-0-9-0`, клиент ждёт `v-0-0-0` — идентификаторы
строятся от uid компонента, и он расходится. Сдвигов это не даёт (Vue не
правит DOM при расхождении атрибута), встречается и на категории, но ломает
`aria-controls` и пачкает консоль. **Приём на будущее:** чтобы увидеть
подробности рассинхрона в прод-сборке, добавьте в `vite.define` этот флаг —
в dev-сборке дефект не воспроизводится вовсе.

**`{ index: false }` НЕ ДАЁТ `noindex`.** `@nuxtjs/robots` перебирает ключи
правила и пропускает всё, чему присвоено `false`
(`useRobotsRule.js`: `if (value === false …) continue`). Закрывать надо
явным `noindex: true`. Из-за этого десять бренд-страниц, которые код считал
закрытыми, лежали в индексе.

**Директивы предпросмотра были у трёх страниц из 310 — и не по замыслу.**
Значение по умолчанию у модуля их УЖЕ содержит, а страницы, объявлявшие
`'index, follow'`, своим объявлением значение по умолчанию ухудшали.

**Правило robots из слэша, двух звёздочек и слэша** появилось от неверного
прочтения отчёта GSC и закрывало `/__og-image__/**` целиком. Питоновский
`robotparser` для проверки НЕ ГОДИТСЯ: у него побеждает первое правило,
у Google — самое длинное. Документ, который это советовал, поправлен.

**Разметка ссылалась на файлы, которых нет:** `/logo.png` и `/og-brand.jpeg`
отдавали 404, первый — из узла `Organization`. Теперь адреса картинок в
`constants/index.ts`, менять их только с проверкой, что файл лежит в `public/`.

## Сессия 19 августа, вторая половина: три отложенных блока переехали на сервер

Закрыт последний крупный пункт. SEO-текст категории, FAQ и отзывы раньше
рисовались только на клиенте — в серверной разметке их не было вовсе, то
есть **для поисковика этого контента не существовало**. Теперь все три
приходят с сервера.

| коммит    | блок      | что мешало                                                               |
| --------- | --------- | ------------------------------------------------------------------------ |
| `66e00c5` | отзывы    | загрузка в `onMounted`                                                   |
| `00fa4a5` | SEO-текст | заглушка `import.meta.server → []` в `seoBlocks`                         |
| `9591561` | FAQ       | `useQuery` (на сервере не идёт) и санитайзер на `document.createElement` |

**Общее правило, ради которого всё и делалось:** обработчик `useAsyncData`
обязан ВОЗВРАЩАТЬ данные, а не раскладывать их по `ref`. Обычный `ref` в
payload не попадает — сервер его наполнит, а клиент при гидратации получит
пустоту. На этой ошибке я попался с `availableBrands`, поэтому в отзывах
сразу сделан `return`.

**Что пришлось починить попутно:** `categoryBrandSeo` переведён из `ref` в
`useState`. Пока SEO-блок был клиентским, расхождение не проявлялось; с
серверным рендером оно дало бы разный текст на сервере и на клиенте.

**Санитайзер FAQ** переписан с DOM на регулярки с тем же правилом (вырезать
`script` и `style`). Специально НЕ использован `useSafeHtml`: он на сервере
возвращает строку как есть, а на клиенте прогоняет через DOMPurify, то есть
даёт разный результат на двух сторонах — в `v-html` это гарантированный
рассинхрон. Отдельно отмечено в коде, что полноценным санитайзером эта
функция не была и раньше: текст ответов пишет администратор.

**Проверено на превью, боевые данные:**

```

/catalog/palatki           3252 знака        | SEO-текст да | FAQ да | CLS 0.0004
/catalog/boys/brand/mattel 2540 знаков       | отзывы да | FAQ да | CLS 0.0000
```

## Сессия 18 августа: разбор последствий переезда бренд-лендингов

Другая машина закрыла пункт №1 прошлой передачи — серверный кеш категорий
(`server/api/categories.get.ts`, замер: 97 КБ и 1.5 с на запрос, 400–650 мс
только на круг до Supabase) и включила ISR категорий, переведя бренд-лендинги
с `?brand=` на путь. Первый байт 0.49 с вместо 2.7–3.8, LCP 2492 мс вместо 4976. Проверка превью запросами нашла три дефекта переезда, все починены.

**Петля редиректов (`b65f220`).** Правило в `vercel.json` совпадало с любым
`/catalog/**`, а платформа переносит исходную query-строку в цель — и цель
снова подходила под то же правило:

```
/catalog/boys?brand=mattel
  → /catalog/boys/brand/mattel?brand=mattel
  → /catalog/boys/brand/mattel/brand/mattel?brand=mattel  → …
```

Восемь шагов и росло: браузер отдал бы ERR_TOO_MANY_REDIRECTS на всех
четырнадцати старых бренд-адресах, которые уже в индексе. Обработчик на Nitro
был написан правильно (пропускает переведённые адреса и удаляет параметр) —
разошлись именно эти два места. Обе защиты теперь описаны в комментарии к
`server/middleware/brand-query-redirect.ts`: JSON комментариев не держит,
и это единственный способ их там удержать.

**Чипы брендов вели в 404 (`b65f220`).** `CategoryBrands` строит ссылки от
`route.path`, а на бренд-лендинге там уже есть хвост — выходило
`/catalog/boys/brand/mattel/brand/hstar`. Нашлось по 404 на префетче
`_payload.json` в консоли. Починено в корне: `buildBrandLandingPath` снимает
прежний хвост, а не наращивает.

**ISR срезает фильтры — НЕ ПОЧИНЕНО, решение за владельцем.** Переезд бренда
на путь снял только половину проблемы: в query остались сортировка и фильтры,
и они ломаются так же. `?sort_by=price_asc` и `?sort_by=price_desc` отдают
побайтово один и тот же порядок, тогда как та же сборка локально сортирует
верно. Клиент не спасает: он слал правильный запрос с `p_sort_by=price_desc`,
но сетка оставалась серверной; локально при том же адресе запросов ноль,
потому что SSR уже отдал правильное.

`allowQuery` **пробовался и не помог** (`eaaf7c4` → откат `40109ce`) —
проверять третий раз незачем. Список доезжает до сборки, это видно в
`.vercel/output/functions/catalog/[...]-isr.prerender-config.json`, но выдача
не меняется: `dest` ISR-маршрута дописывает `?__isr_route=` и затирает
исходную query раньше. Проверено и по алиасу, и по прямому адресу деплоя.

Выбор, который остаётся: **либо ISR** (первый байт 0.49 с, LCP 2492 мс) и
неотсортированная выдача по прямой ссылке с фильтром, **либо фильтры в SSR**
и первый байт 2.7–3.8 с. Сейчас оставлен ISR — внутри сайта фильтры работают
(переход клиентский, сервера не касается), фильтрованные адреса закрыты
`noindex`, ломается только прямой заход по присланной ссылке. Третий путь,
если владелец захочет и то и другое: заставить клиент перечитывать параметры
из `window.location` после гидратации и перерисовывать сетку — работа в
`composables/useCatalogQuery.ts` и на странице категории, с риском мигания.

**Закрыто замером и уборкой (вторая половина 18 августа).**

- **Speed Index категории** — прежняя худшая метрика сайта — ушёл с 7.8 до
  5.2 с; TTFB упал до 5–15 мс. Пункт закрыт.
- **Рост TBT главной регрессией не был:** медиана 189 при разбросе 106–329.
  Метрика шумная, выводы по одному прогону делать нельзя.
- **CLS категории скачет между прогонами** (0.0018 в двух, 0.0900 в двух
  других подряд) — ещё одно подтверждение, что цифра лабораторная.
- **LCP категории 2492 мс не воспроизводится:** шесть прогонов дают
  3151–6151, медиана около 4.9 с. Улучшение против 8.7 с настоящее, но 2492
  в комментарии к `routeRules` — разовая удача, не рабочее значение.
- **Мёртвый `CategoryDescription.vue` удалён** (`6421c20`), и вместе с ним
  три мёртвых и заведомо сломанных OG-шаблона (`d4e71dd`). Проверено, что
  дырки в OG-разметке нет: у всех ключевых страниц `og:image` отдаётся,

**Чем проверять при следующем касании этой области.** Цепочка со старого
`?brand=` обязана кончаться за один шаг; ссылки брендов на лендинге обязаны

что фильтры в SSR наконец заработали: `?sort_by=price_asc` и

Две ловушки, на которых тут уже ошибались:

## LCP категории: разобран, упирается в сеть

Разбор 19 августа. Итог короткий: **LCP на категории равен FCP**, картинка ни
при чём, процессор ни при чём, дальнейшее ужатие payload ничего не даст.

**Шкала одного прогона** (профиль Lighthouse: Slow-4G, CPU ×4):

```
первый байт HTML       500 мс   (сервер отвечает за 11 мс, остальное DNS+TCP)
HTML дочитан          1590 мс
весь CSS готов        1678 мс
картинка LCP дочитана 2863 мс
первая отрисовка      3960 мс   ← здесь же и LCP
```

Картинка загружена за секунду до первой отрисовки — оптимизировать её
бессмысленно. Элемент LCP это `<img>` первой карточки, и он уже на месте.

**Сеть против процессора** — развели экспериментом:

| условия                     | FCP          |
| --------------------------- | ------------ |
| Slow-4G + CPU ×4            | 2676         |
| Slow-4G, процессор свободен | 2408 (−268)  |
| сеть свободна, CPU ×4       | 1196 (−1480) |

Процессор почти ни при чём.

**Вес документа влияет, но слабо.** Медианы трёх прогонов: `/about` (40 КБ) —
FCP 2196 мс, `/catalog/boys` (329 КБ) — 2732 мс. Восьмикратная разница в весе
стоит ~540 мс, а разброс лёгкой страницы (1560–2724) перекрывает тяжёлую
целиком. Значит есть **пол около 2 секунд**, не зависящий от страницы: DNS
130 мс, TCP 251 мс, круги по 150 мс на каждый запрос в эмуляции.

**Дальше payload резать бесполезно — проверено.** В нём осталось 125 строк
категорий (63 в общем списке плюс столько же копий в дереве меню) со всеми
SEO-полями. Это 35.7 КБ сырьём, 24% payload — но **всего 0.9 КБ по проводу**:
поля почти сплошь `null` и повторяющиеся имена ключей, brotli их схлопывает.

**Что сделано по итогам разбора** (`48eec3d`): описания товаров в списках
режутся до 200 знаков — ровно столько берёт разметка Schema.org, и только у
первых десяти товаров. Документ 348 → 329 КБ сырьём, 43.7 → 39.7 КБ по
проводу. На метрику это не повлияло: 4 КБ по проводу — это 20 мс, тонет в
шуме. Правка полезна сама по себе, но LCP не двигает.

**Вывод: лабораторный LCP категории (~2.7–2.9 с) определяется константами
эмуляции, а не кодом.** Чтобы понять, что видят настоящие посетители, нужны
полевые данные, а CrUX по домену их не даёт — трафика не хватает. Следующий
осмысленный шаг здесь не оптимизация, а измерение реальных пользователей.

## Технический долг — принятые решения

Не «руки не дошли», а осознанный выбор владельца. Не переигрывать без его
слова и не предлагать «починить» в отчётах.

### Индексация бренд-страниц без товара — решено 20 августа 2026

**Правило:** бренд без единого активного товара закрывается `noindex` и не
попадает в карту сайта, **кроме** перечисленных в
`BRANDS_KEPT_INDEXABLE_WITHOUT_PRODUCTS` (`constants/index.ts`).

Владелец выбрал формулировку «закрывать все, кроме тех, что дают показы».
Применено к данным Search Console за 90 дней (21 мая — 18 августа 2026):

```
показы есть → остаются открытыми (8):
  mg-toys 41 показ поз 2.6 | eva-puzzle 90 поз 6.0 | koala-diary 15 поз 6.2
  bowa 11 поз 2.8 | fivestar-toys 11 поз 9.2 | soba 2 поз 6.5
  rc-toys 1 поз 6.0 | shantou-yisheng 1 поз 8.0

показов нет вовсе → закрыты (2):
  air-blaster, polese
```

**Две поправки, на которых я по дороге ошибся — не повторять:**

- различие «нет в наличии» против «совсем пустой» на этих данных ПУСТОЕ:
  у всех десяти брендов ноль активных товаров, а не только ноль остатка;
- показы дают ВОСЕМЬ из десяти, а не два, как я сперва предположил.

Список — снимок данных. Пересматривать при следующем заходе в Search Console:
у бренда мог появиться товар (тогда строка ничего не значит) или пропасть
спрос. Условие продублировано в `pages/brand/[slug].vue` и
`server/api/sitemap-routes.ts` — обе стороны читают одну константу, чтобы не
разъехались.

### `/catalog/new` в карте сайта только с товарами — решено 20 августа 2026

Страница попадает в sitemap, **только если в базе есть товары с `is_new`**.
На момент решения их ноль, страница показывает «Пока нет новинок», и Google
уже поставил ей «Crawled — currently not indexed».

Наполнять её товарами или нет — вопрос к админке, не к коду. Как только
товар пометят новинкой, адрес вернётся в карту сам, без правок.

Отдельно и НЕ сделано: `useAsyncData` там вызван с `{ lazy: true }`, то есть
отрисовка не ждёт данных. Даже когда новинки появятся, в серверную разметку
они не попадут — это чинить отдельной веткой.

### Перекодировка blur-подложек отменена, сделано иначе

**Решено 19 августа: в прод не пишем.** Прежняя оценка «подложки можно
ужать вчетверо, до 300–600 байт» оказалась **неверной** — она была из общих
соображений, а не из замера.

Замер на боевых данных (1046 подложек товаров, 1604 КБ, медиана 1559 байт):
предел кодировщика WebP в Chromium — около **770 байт независимо от размера
картинки**. У формата фиксированный заголовок, плюс треть сверху добавляет
base64. JPEG в этом диапазоне ещё хуже (1065+ байт). То есть перекодировка
дала бы экономию вдвое, а не вчетверо, ценой переписывания 1046 строк в
боевой базе.

Вместо этого сделано то, что дало больше и без записи в прод (`abd3fe5`):
заглушки получают только первые четыре товара списка — столько же, сколько
карточек грузит картинку жадно. Ниже сгиба заглушка бесполезна: пока до
карточки долистают, картинка уже загружена.

Отдельно: генерировать подложки без `sharp` можно канвасом в Chromium через
Playwright — приём рабочий, проверен на боевых картинках. Пригодится, если
понадобится массовая перегенерация по другой причине.

### Фильтры не доезжают до сервера под ISR

**Решено 19 августа 2026: оставляем как есть, вносим в техдолг.**

Суть: правило `'/catalog/**': { isr: 1800 }` даёт первый байт 0.49 с вместо
2.7–3.8 с, но vercel-пресет подменяет query-строку в маршруте ISR-функции.
Из-за этого по прямой ссылке с `?sort_by=` или другим фильтром сервер
отдаёт нефильтрованную выдачу: `?sort_by=price_asc` и `?sort_by=price_desc`
возвращают побайтово один и тот же порядок товаров.

Почему приемлемо: внутри сайта фильтры работают — там переход клиентский и
сервера не касается. Ломается только прямой заход по присланной или
сохранённой ссылке с параметром, а такие адреса и так закрыты `noindex`.

Что уже проверено и не сработало, чтобы не пробовали снова:

- `allowQuery` в правиле ISR (`eaaf7c4`, откачен `40109ce`). Список доезжает
  до сборки — виден в `.vercel/output/functions/catalog/[...]-isr.prerender-config.json`, —
  но выдача не меняется: `dest` ISR-маршрута дописывает `?__isr_route=` и
  затирает исходную query раньше. Проверено и по алиасу, и по прямому адресу
  деплоя.

Чем платить, если решение когда-нибудь переиграют: снять ISR — вернётся
первый байт 2.7–3.8 с на всём каталоге. Третий путь — заставить клиент
перечитывать параметры из `window.location` после гидратации и
перерисовывать сетку; работа в `composables/useCatalogQuery.ts` и на
странице категории, с риском мигания выдачи.

## Что осталось, по приоритету

### 1. Скрипты: жадный чанк 895 → 712 КБ, что осталось

**Сделано** (`97974c0`, `23f9ddf`, `3b3b569`): жадный чанк, который грузится
на каждой странице до гидратации, **895 → 712 КБ (−20%)**. Что сработало:

- префикс `Lazy` у четырёх модалок в `app.vue` (−24 КБ). `shouldMountModals`
  и так поднимался по `requestIdleCallback`, но откладывал только
  монтирование: код автоимпортированного компонента без `Lazy` всё равно
  лежал в жадном чанке;
- `vaul-vue` отпущен из общего `vendor` (−23.5 КБ). Одно без другого не
  работает: пока библиотека приколочена к vendor, ленивость компонента
  ничего не меняет;
- удалены четыре мёртвых компонента из `components/global/` (37 КБ
  исходников), а `DynamicFilters` оттуда переехал — глобальная регистрация
  отменяла ленивость, хотя страница каталога импортирует его динамически.

**Закрыто (`3b3b569`): reka-ui уехал из жадного чанка, 844 → 712 КБ.**
Итог по скриптам за сессию — **895 → 712 КБ, это −20%**.

Нашлось вытаскиванием графа импортов. Приём стоит запомнить, он же
пригодится для следующего: плагин Rollup на `generateBundle` даёт реальный
состав чанка через `entry.modules` (с `renderedLength`), а
`this.getModuleInfo(id).importers` — статических импортёров. Сопоставив
модули с чанками, видно, кто именно жадный.

Из 81 импортёра бочки `reka-ui/dist/index.js` в жадном чанке был ровно один:

```
app.vue → LoadingBar.vue (в components/global/, значит глобальный и жадный)
        → @/components/ui/progress → бочка reka-ui → 157 модулей, 309.5 КБ
```

Бочка статически реэкспортирует всю библиотеку, поэтому одна полоска
загрузки тащила Select, Slider, Listbox и Menu, нужные только админке и
фильтрам. Лечится ДВУМЯ правками, работающими только вместе: LoadingBar
рисует полоску своей разметкой, и reka-ui отпущен из `vendor` в
`manualChunks`. По отдельности каждая даёт ноль — пока жадный импортёр есть,
Rollup кладёт библиотеку во входной чанк, что бы ни говорил `manualChunks`.
Из-за этого прошлые попытки отпустить reka-ui и выглядели безрезультатными.

**Замер после этих правок ничего не показал — и это тоже результат.**
Медианы трёх прогонов до и после (мобильные, превью):

|                      | perf    | FCP         | LCP         | SI          | TBT       |
| -------------------- | ------- | ----------- | ----------- | ----------- | --------- |
| главная до / после   | 71 / 71 | 3601 / 3451 | 4501 / 4426 | 4411 / 5751 | 189 / 171 |
| категория до / после | 71 / 65 | 3976 / 3976 | 6151 / 6151 | 5238 / 5395 | 60 / 107  |
| карточка до / после  | 68 / 68 | 4051 / 4351 | 5476 / 5476 | 4474 / 4351 | 130 / 91  |

Всё внутри шума: разброс perf по прогонам 63–77, TBT 32–214. Что-то чуть
лучше, что-то чуть хуже, приписать это минус 20% жадного JS нельзя.

Вывод для следующей сессии: **вес бандла и баллы Lighthouse на этом сайте
связаны слабо**. Выигрыш по весу реален и измерен напрямую (чанк 895 → 712 КБ,
жадный путь 969 → 857 КБ на превью), но FCP и LCP здесь упираются в сеть и
картинки, а TBT и так низкий. Гнаться дальше за килобайтами ради баллов
смысла мало — если браться, то ради времени на слабых устройствах, и мерить
надо не PSI, а профилем главного потока.

**Ещё не пробовано и, возможно, проще:** `vue-sonner` (22.7 КБ) держится
75 файлами, импортирующими `toast`. Обёртка-хелпер с ленивым импортом
внутри убрала бы библиотеку из жадного чанка, но это правка 75 мест.

**Осторожно:** разделение чанков на этом проекте уже давало рантайм-ошибку
`ReferenceError` из-за циклических зависимостей. Ядро (`vue`, `vue-router`,
`pinia`, `supabase`) не трогать. Проверять надо и админку тоже.

- `.env` смотрит в **локальную** базу (`127.0.0.1:54321`), а превью

## Скрипт, которым мерился вес документа

Кладётся в корень репозитория, после работы удаляется.

```js
import { brotliCompressSync } from 'node:zlib'

for (const url of process.argv.slice(2)) {
  const html = await (
    await fetch(url, {
      headers: {
        'user-agent': 'Mozilla/5.0 (Linux; Android 11) Chrome/140 Mobile',
      },
    })
  ).text()
  const br = s => brotliCompressSync(Buffer.from(s)).length
  const stripped = html.replace(/"data:image[^"]*"/g, '""')
  const uris = [...html.matchAll(/"(data:image[^"]*)"/g)].map(m => m[1])
  console.log(`\n${url}`)
  console.log(
    `  brotli ${(br(html) / 1024).toFixed(1)} КБ → без data:URI ${(br(stripped) / 1024).toFixed(1)} КБ`,
  )
  console.log(
    `  data:URI: ${uris.length} шт, сырьём ${(uris.reduce((s, u) => s + u.length, 0) / 1024).toFixed(1)} КБ`,
  )
}
```

Заголовок `x-vercel-cache` смотреть тем же `fetch` — им и обнаружился `MISS`
на категориях против `HIT` на главной.
