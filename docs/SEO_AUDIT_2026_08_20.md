### 1. CLS бренд-страниц — от 0.03 до 0.24 при пороге 0.1

Измерено пассивно в браузере (`PerformanceObserver`, из DOM до конца прогона
ничего не читается — на этой ошибке здесь уже спотыкались):

| страница        | 412 px     | 1440 px    |
| --------------- | ---------- | ---------- |
| `/brand/mattel` | **0.2427** | **0.1099** |
| `/brand/zuru`   | **0.1703** | **0.1114** |
| `/brand/lego`   | 0.0517     | **0.1680** |
| `/brand/cada`   | 0.0603     | 0.0293     |

Порог «хорошо» — 0.1. Три бренда из четырёх его превышают хотя бы на одном
разрешении. Для сравнения, остальные типы страниц чистые: главная 0.0015 /
0.0060, категория 0.0013 / 0.0092, каталог 0.0170 / 0.0008, карточка товара
0.0224 / 0.0223.

**Почему это важнее прочего в списке.** По данным Search Console за 28 дней
бренд-страницы — главный вход из поиска: `/brand/cada` (6 кликов, 101 показ,
позиция 5.2), `/brand/zuru` (79 показов), `/brand/huanger`, `/brand/eva-puzzle`,
`/brand/lego/lego-one-piece`. Пять из пятнадцати верхних адресов — бренды, и
первое место среди них тоже. Именно эти страницы и не проходят по CLS.

**Поправка к прежней записи.** В HANDOFF за 19 августа значится, что CLS
бренд-лендинга починен и даёт 0.0004 в трёх пассивных прогонах подряд. На
проде сегодня это не так. Та проверка делалась на превью; на боевой сборке
цифры выше на два порядка. Правка `8540eab` (перенос трёх клиентских блоков
ниже серверных) сама по себе разумна, но проблему она не сняла.

### 2. Рассинхрон гидратации на бренд-лендинге

`Hydration completed but contains mismatches` — ошибка в консоли на
`/brand/mattel` **на обоих разрешениях** и на `/brand/cada` на десктопе.
Ловится и браузером, и Lighthouse (в отчёте PSI по десктопу она же).
Остальные пять проверенных типов страниц консоль не пачкают.

Скорее всего это и есть источник сдвигов из пункта 1: при расхождении Vue
перерисовывает поддерево, а перерисовка двигает вёрстку.

Куда смотреть. В `pages/brand/[slug].vue` данные раскладываются по обычным
`ref` — `brandProductLines` (строка 66) и `brandStats` (строка 87), оба
наполняются из `watchEffect`, а не возвращаются из `useAsyncData`. Это ровно
тот случай, который описан в HANDOFF как общее правило: обычный `ref` в
payload не попадает, сервер его наполнит, а клиент при гидратации получит
пустоту. Дополнительный подозреваемый — `productsStore` с
`pinia-plugin-persistedstate`: на клиенте состояние поднимается из
localStorage и может отличаться от того, из чего рисовал сервер.

Точный узел не локализован: боевая сборка Vue деталей расхождения не печатает,
а сравнение серверной разметки с DOM после гидратации показывает только
ожидаемые клиентские вставки (мобильная нижняя навигация, замена скелетонов).

### 3. Ошибка разметки отзывов — вердикт Google FAIL на 11 страницах

Search Console по адресу
`/catalog/constructors-root/konstruktory-malchikam/brand/mg-toys`:

```
Review snippets   ERROR   Invalid object type for field "<parent_node>"
вердикт: FAIL
```

Причина: `aggregateRating` подвешен к узлу `CollectionPage`.

```json
{ "@type": "CollectionPage", "aggregateRating": { "@type": "AggregateRating", "ratingValue": 5, "reviewCount": 2 } }
```

`CollectionPage` не входит в список типов, для которых Google поддерживает
сниппет с отзывами. Разметка есть, но звёзды в выдаче по ней не появятся, а
страница числится с ошибкой.

Переобход всех 310 адресов: **такой узел на 11 страницах** — это те, у которых
есть отзывы, и число будет расти вместе с отзывами:

```
/catalog/boys                          /catalog/girls/kukly
/catalog/girls                         /catalog/girls/kukly/kukly-lol
/catalog/boys/interaktivnye-igrushki   /catalog/constructors-root/konstruktory-malchikam
/catalog/constructors-root/konstruktory-malchikam/brand/{lego, mg-toys, play-smart, sluban}
и ещё одна
```

По `/catalog/boys` Google пока показывает «Review snippets, 0 замечаний» —
но её последний обход 3 августа, а обход mg-toys был 19 августа. Разметка у
них одинаковая, так что расхождение объясняется датой обхода, а не разницей
страниц.

### 4. Каталог отдаёт `200` на любой родительский путь

Маршрут `pages/catalog/[...slug].vue` ищет категорию по последнему сегменту и
не проверяет остальные:

| запрошенный путь                                        | код | canonical                                        |
| ------------------------------------------------------- | --- | ------------------------------------------------ |
| `/catalog/constructors-root/konstruktory-malchikam`      | 200 | сам на себя                                      |
| `/catalog/constructors/konstruktory-malchikam`           | 200 | `/catalog/constructors-root/konstruktory-malchikam` |
| `/catalog/vydumannaya-kategoriya/konstruktory-malchikam` | 200 | `/catalog/constructors-root/konstruktory-malchikam` |
| `/catalog/boys/konstruktory-malchikam`                   | 200 | `/catalog/constructors-root/konstruktory-malchikam` |
| `/catalog/konstruktory-malchikam`                        | 200 | `/catalog/constructors-root/konstruktory-malchikam` |

Смягчающее обстоятельство: canonical везде правильный, и Google склеит эти
адреса. Но пространство адресов бесконечно, и каждый выдуманный путь — это
страница, которую робот скачивает целиком (медиана документа тут 242 КБ),
чтобы затем выбросить.

**Это не теория.** В Search Console за 28 дней показы получают именно такие
адреса: `/catalog/constructors/konstruktory-malchikam?brand=cada` (позиция
6.3, 1 клик) — сегмента `constructors` в базе нет, есть `constructors-root`.
То есть Google уже обходит и ранжирует варианты с несуществующим родителем.

Правильное поведение — `301` на канонический путь либо `404`. Цепочка со
старого `?brand=` при этом здорова: один переход, дальше `200` с верным
canonical — проверено на трёх адресах из отчёта GSC.

### 5. Бренд-страницы без товара: намерение `noindex` не срабатывает

`pages/brand/[slug].vue:557` объявляет правило так:

```ts
computed(() => ({ index: brandHasStock.value !== false, follow: true }))
```

При отсутствии товара в наличии выходит `{ index: false, follow: true }`, а
`@nuxtjs/robots` печатает из этого **просто `follow`** — директивы `noindex`
в выдаче нет ни в мета-теге, ни в заголовке:

```
/brand/rc-toys           x-robots-tag: follow
/brand/shantou-yisheng   x-robots-tag: follow
/brand/mattel            x-robots-tag: index, follow
```

Для робота `follow` без `noindex` означает индексировать. Таких страниц
**десять**: `air-blaster`, `bowa`, `eva-puzzle`, `fivestar-toys`,
`koala-diary`, `mg-toys`, `polese`, `rc-toys`, `shantou-yisheng`, `soba`.
Все десять при этом лежат в карте сайта — то есть карта и код противоречат
друг другу.

**Прежде чем чинить — решение владельца, а не автоматика.** Эти страницы
приносят трафик: `/brand/eva-puzzle` — 1 клик и 15 показов на позиции 5.0 за
28 дней, `/brand/rc-toys` в индексе («Submitted and indexed»). Починка бага
уберёт их из выдачи. Вариантов два, и выбор не технический: либо закрывать
как задумано и терять эти входы, либо оставлять открытыми и тогда убрать из
кода нерабочее правило, чтобы оно не вводило в заблуждение.

### 6. `/catalog/new` — пустая страница в карте сайта

Google уже вынес вердикт: **«Crawled — currently not indexed»**, последний
обход 10 апреля. Причина видна сразу:

- в серверной разметке **29 слов**, товаров нет вовсе, `ItemList` нет;
- в браузере после загрузки — «Пока нет новинок», карточек ноль;
- в базе действительно нет ни одного товара с `is_new = true`;
- `og:image` пустой.

То есть в карту сайта отправляется заведомо пустая страница. Отдельно, на
будущее: `useAsyncData` там вызван с `{ lazy: true, server: true }`
(`pages/catalog/new.vue:52`), а `lazy` означает «не ждать до отрисовки» — даже
когда новинки появятся, в серверную разметку они не попадут.

### 8. `Disallow: /**/` в robots.txt закрывает лишнее

Правило стоит в `nuxt.config.ts:248` явно. По алгоритму Google (побеждает
самое длинное совпадение) оно перекрывает **любой путь из двух и более
сегментов**, кроме спасённых более длинными `Allow: /catalog/**` и
`Allow: /brand/**`:

| путь                                      | вердикт  | правило                   |
| ----------------------------------------- | -------- | ------------------------- |
| `/catalog/boys/mashinki`                  | разрешён | `Allow: /catalog/**`      |
| `/brand/mattel/barbie`                    | разрешён | `Allow: /brand/**`        |
| `/__og-image__/image/catalog/boys/og.png` | ЗАПРЕЩЁН | `Disallow: /**/`          |
| `/promo/<любой-slug>`                     | ЗАПРЕЩЁН | `Disallow: /**/`          |

Под запрет попали **все генерируемые OG-картинки** — а на них ссылается
`og:image` каталога, всех категорий, бренд-разделов и `/brands`. Соцсети
robots.txt в основном игнорируют, так что превью в мессенджерах живы, но для
Google эти картинки недоступны.

Маршрут `/promo/[slug]` существует в коде; живых ссылок на него сейчас в
разметке нет, так что потерь пока нет — но страница, сделанная по этому
маршруту, окажется закрытой.

Проверять такое питоновским `robotparser` бесполезно: у него побеждает первое
подходящее правило, и он говорит, что разрешено всё, включая `/admin`.

### 9. `max-image-preview:large` — только на 3 страницах из 310

```
/brands, /privacy-policy, /returns   index, follow, max-image-preview:large, max-snippet:-1, max-video-preview:-1
остальные 307                        index, follow
```

Для магазина игрушек это прямая упущенная выгода: без директивы Google
показывает в выдаче маленькую квадратную миниатюру вместо крупной картинки.
Товарных карточек это касается в первую очередь. Три страницы получили
директиву не по замыслу, а потому что на них она прописана иначе.

### 11. Разметка товара — предупреждения Google

По карточке товара и по категории Search Console отдаёт:

```
Product snippets     WARNING  Missing field "aggregateRating"
Product snippets     WARNING  Missing field "review"
Merchant listings    WARNING  Missing field "validFrom"
```

Это предупреждения, не ошибки — карточка проходит с вердиктом PASS. Но
`aggregateRating` нет на **174 карточках из 178**: отзывов у товаров почти
нет, а значит и звёзд в выдаче нет. `validFrom` не хватает в
`priceSpecification` со скидочной ценой.

В остальном разметка товара сильная и трогать её не надо: `offers` с
`priceValidUntil`, `itemCondition`, `seller`, `hasMerchantReturnPolicy` (14
дней, бесплатный возврат) и `shippingDetails` с временем сборки и доставки.

Мелочи в данных: `sku` и `mpn` равны `"HiH02 "` — с висячим пробелом из базы;

### 13. Неиспользуемый JavaScript

На каждой из шести проверенных страниц Lighthouse показывает **176–186 КБ**
неиспользуемого JS и оценивает экономию в 0.45–1.35 секунды. Это продолжение
уже известного пункта про жадный чанк (895 → 712 КБ). Напомню вывод прошлой
сессии, он остаётся в силе: вес бандла и баллы на этом сайте связаны слабо,
браться за это стоит ради слабых устройств, а не ради цифры в отчёте.

### 14. Два узла `Organization` с разными `@id`

На каждой странице отдаются `#identity` (от `nuxt-schema-org`, `sameAs`
пустой, ни логотипа, ни телефона) и `#organization` (свой, полный: логотип,
Instagram, `legalName`, `foundingDate`), плюс отдельный `#store` с
координатами, телефоном и часами работы.

Опасности меньше, чем кажется: и `WebSite.publisher`, и `WebPage.about`
ссылаются на `#organization`, то есть на полный узел. `#identity` — сирота, на
него не ссылается никто. Но описывать один бизнес двумя сущностями всё равно
не стоит.

## Что проверено и оказалось в порядке

- **Все 310 адресов карты отдают `200`.** Ни одного `404`, `500` или редиректа.
- **`canonical` у всех 310 указывает на себя.** Расхождений ноль.
- **`noindex` в карте нет ни одного.**

  потеряно и ничего лишнего.

## Чего этот аудит НЕ покрыл

- **Реальные посетители.** CrUX по домену пуст, поэтому все цифры скорости —
  лабораторные. Что видят живые люди, по-прежнему неизвестно.
- **Страницы за логином.** `/profile/**` в этот аудит не входили — проверялись
  отдельно 19 августа.
- **Замеры по одному прогону** для трёх из шести страниц: по категории,
  карточке и главной сделано по три прогона, по `/catalog`, `/brand/mattel` и
  `/brands` — по одному, и доверять им как числам нельзя.
- **Причина медленного LCP карточки товара** не разобрана. Известно только,
  что цифра устойчивая (58–60 perf в трёх прогонах). Прошлый разбор LCP
  делался по категории, и вывод «упирается в сеть» на карточку автоматически
  не переносится — там своя картинка и своя галерея.
- **Точный узел рассинхрона гидратации** не найден, есть только подозреваемые.
- **Внешние ссылки, конкуренты, семантика** — не смотрел вообще, это отдельная
  работа.
- **Яндекс и Bing** — вебмастера не проверялись, только `Clean-param` в
  robots.txt глазами.
- **Админка** — в аудит не входила.

## Порядок работ, если браться

Ветки заводятся по правилу из CLAUDE.md, каждая правка отдельно.

1. `fix/*` — рассинхрон гидратации и CLS бренд-страниц (пункты 1–2). Самое
   дорогое по последствиям: страдают главные страницы входа.
2. `fix/*` — `aggregateRating` убрать с `CollectionPage` (пункт 3). Дёшево,
   снимает вердикт FAIL с 11 адресов.
3. `fix/*` — `Allow: /__og-image__/**` в robots.txt либо замена `/**/` на
   правило с якорем (пункт 8). Одна строка.
4. `feat/*` — `max-image-preview:large` на все индексируемые страницы (пункт 9).
5. **Решение владельца, не правка**: что делать с десятью бренд-страницами без
   товара (пункт 5) и с `/catalog/new` (пункт 6).
6. `fix/*` — `301` вместо `200` на неверный родительский путь в каталоге
   (пункт 4). Требует аккуратности: тронуть легко, сломать выдачу тоже.
7. Разбор LCP карточки товара — не правка, а измерение: снять шкалу одного
   прогона так же, как это делалось для категории, и понять, упирается ли
   карточка в сеть или в свою галерею.
8. Гигиена: пункты 10–12, 14 — можно одной `refactor/*`, кроме `og:image`,
   который относится к поведению.

Запрос на переобход `/about` в Search Console (пункт 7) правок в коде не
требует.
