## Что осталось, по приоритету

### ~~1. Имя автора отзыва не показывается никогда~~ — закрыто

**Сделано и применено на прод 14 августа.** Миграция `20260813120000_review_author_names.sql` числится в `supabase_migrations.schema_migrations`; сверка репозитория с базой — 349 файлов против 349 записей, расхождения нет ни в одну сторону. Проверено вызовом RPC анонимным ключом: возвращаются реальные имена вместо запасного «Покупатель».

Всплыло сразу после починки блока отзывов (`44c5783`) и в самом коммите не решается.

У таблицы `profiles` **нет ни одной политики чтения для анонимов**: есть только «Users can view own profile» (`auth.uid() = id`) и «Admins can view all profiles». Обе функции отзывов объявлены `SECURITY INVOKER`, поэтому `LEFT JOIN profiles` у гостя не находит ничего, и `user_name` всегда сваливается в запасное «Покупатель».

При этом имена заполнены: на проде 9 профилей из 9 имеют `first_name`/`last_name`. То есть данные есть, их просто не отдают.

То же ограничение действует и на карточке товара: `stores/publicStore/reviewsStore.ts` подтягивает `profiles!product_reviews_profile_id_fkey(first_name, last_name, avatar_url)` тем же анонимным клиентом.

Из двух путей выбран первый:

- **`SECURITY DEFINER` с зафиксированным `search_path`** — имя отдаёт функция, таблица остаётся закрытой целиком;
- ~~RLS-политика на `profiles`~~ — отклонено. RLS открывает **строку**, а не колонку, то есть вместе с именем анониму достались бы `phone`, `telegram_chat_id`, `active_bonus_balance`, `pending_bonus_balance`, `role`. Ограничить состав колонок можно только отзывом табличного `GRANT` у роли `anon`, а он выдан на всю таблицу по умолчанию.

Решение не новое: `get_reviews_by_brand` (`20260313000001`) отдаёт имена на страницах брендов ровно так же с марта. То есть на брендах имена показывались, а на категориях и в карточке — нет; это выравнивание, а не открытие ранее закрытых данных.

Что сделано:

- `get_latest_category_reviews` → `SECURITY DEFINER` (тело не тронуто);
- новая `get_product_reviews(uuid)` для карточки — состав полей и сортировка повторяют прежний `REVIEW_SELECT`, поэтому компоненты не менялись;
- `get_reviews_by_brand` заодно получила фиксированный `search_path`: она была `DEFINER` без него с марта.

Проверено на локальной базе, приведённой к прод-состоянию этих функций. До правки аноним получал пять «Покупатель», после — реальные имена; `profiles` для анонима по-прежнему отдаёт 0 строк; немодерированный отзыв через функцию не проходит. Отдельно проверен реальный HTTP-вызов через PostgREST ключом `anon`: состав ключей совпадает с `ProductReview`, `profiles` приходит объектом, `review_images` — массивом с сортировкой по `display_order`.

### ~~2. Блок отзывов появляется в зависимости от пагинации~~ — закрыто

**Сделано**, коммит `d03d7ed`. Условие показа теперь `v-if="currentCategory"`, а решение принимает сам компонент по данным всей категории.

Было так: `categoryStats` суммировал `review_count` по `displayedProducts` — то есть только по товарам **текущей страницы выдачи**, — а `v-if` блока был завязан на `categoryStats.reviews > 0`.

Отсюда: на `/catalog/kukly-lol` и `/catalog/boys` блок есть, а на `/catalog/girls` его нет, хотя отзывы в этой категории имеются — товар с ними просто не попал на первую страницу. Смена фильтра или страницы блок то показывает, то прячет.

Сами RPC считают по всему поддереву категории и от пагинации не зависят — расходится именно условие показа.

### Сверх аудита: мягкие 404 — закрыто

В аудите этого не было, нашлось 15 августа при проверке категорий. Ветка
`fix/catalog-soft-404`.

**Категории.** `/catalog/<любой-мусор>` отвечал HTTP 200, заголовок собирался
из самого слага («qwerty zzz 999 купить в интернет-магазине Ухтышка…»), а в
мете стояло `robots: index, follow`. То есть сайт сам порождал неограниченное
число индексируемых страниц-пустышек: любая опечатка в ссылке и любой битый
адрес из чужой выдачи становился отдельной тонкой страницей.

**Карточки товара.** Там `createError` стоял с самого начала, но не работал:
`throw` внутри обработчика `useAsyncData` Nuxt перехватывает и кладёт в
`error`, рендер продолжается. `/catalog/products/<мусор>` отдавал 200 с
заголовком «Товар | Ухтышка». Спасал только `noindex` в мете, но статус
обязан быть 404.

Обе проверки написаны так, чтобы **сбой загрузки не превращался в 404**:
у категорий условие требует непустого списка категорий, у товара ошибка
запроса отделена от пустого ответа и отдаёт 503. Иначе разовый сбой осел бы
в SWR-кеше маршрута и раздавался бы как 404 всем, включая робота.

### ~~4. Анонимный посетитель подписывается на каналы заказов~~ — закрыто

**Сделано**, ветка `fix/realtime-guest-subscriptions`. Только фронт, миграции не нужны.

`app.vue` звал `subscribeAll()` из `useOrderRealtime` безусловно — без проверки роли и факта авторизации. На каждой странице у каждого гостя открывался WebSocket и две подписки `postgres_changes` на `orders` и `guest_checkouts`.

**Поправка к первой редакции пункта.** Там было написано, что в консоль летит `❌ Error subscribing to orders channel: undefined`. В живом браузере на `dev.uhti.kz` этого нет: канал отвечает `phx_reply status: ok`, приходит `system: Subscribed to PostgreSQL`, в консоли `✅ Subscribed to orders channel`. Ошибка была артефактом песочницы PageSpeed — там же рядом висел `ERR_NAME_NOT_RESOLVED` на самом WebSocket, про который в первой редакции честно стояло «не уверен». Проверено в живом браузере, как и предполагалось: подписка не падает.

То есть чинилась не ошибка, а бесполезная работа. Событий гость не получал никогда: RLS у `orders` и `guest_checkouts` не отдаёт анониму ни одной строки (REST на обе таблицы отвечает `[]`), а `postgres_changes` применяет ту же RLS к каждому подписчику. Соединение висело, событие не приходило.

Теперь подписка открывается только при `profileStore.isAdmin`, и не разово на `mount`, а по `watch`: профиль подгружается отложенно, и на момент монтирования роль неизвестна даже у вошедшего администратора.

Проверено на собранном приложении: у гостя **0 WebSocket-соединений** и ни одного события каналов, было — 1 соединение и 2 подписки. Путь администратора в браузере **не проверен**: вход через Google OAuth агенту недоступен, покрыт 4 юнит-тестами.

**Замечание в сторону.** Задумка композабла — «обновить остатки, когда заказ подтверждён» — для покупателей не работала никогда по той же причине (RLS). Эта правка её не чинит, а убирает цену. Если остатки должны обновляться у покупателей, это другая конструкция: broadcast-канал или realtime на самой таблице `products`.

### ~~5. LCP категории — 11.5 секунды на мобиле~~ — причина найдена и закрыта

**Закрыто 15 августа**, ветка `perf/lcp-eager-image-reveal`. Причина оказалась
не в тех трёх рычагах, что перечислены ниже, — они все про сеть, а метрику
держало другое.

#### Настоящая причина: LCP-картинка приходила прозрачной

`ProgressiveImage` рисовал `<img>` с классом `opacity-0` и снимал его только
по событию `@load`, то есть **в браузере и только после гидратации**. А элемент
с нулевой прозрачностью не может стать LCP по определению метрики.

Отсюда разрыв, который и был всё это время виден в трассах, но не объяснён:

```
картинка первой карточки скачана   6.2 с
LCP зафиксирован                  13.1 с
```

Семь секунд между «файл есть» и «метрика сработала» — это ожидание главного
чанка в 273 КБ и его разбора на CPU ×4. Всё, что делалось раньше — SSR сетки
(`e8b8541`), preload картинки (`667cc79`), урезание payload (`9642372`), —
работало правильно и до метрики не доходило: картинка была на месте, скачана
вовремя и невидима.

В разметке `/catalog/boys` таких `<img>` было 12 из 12 — вся сетка.

#### Правка

`opacity-0` больше не вешается на `eager`-картинки: они над сгибом, рисуются
по мере декодирования, а до этого сквозь прозрачную `<img>` виден LQIP-слой
под ней. Плавное проявление осталось у ленивых картинок, где оно и заметно.

Заодно `<picture>` получил `relative`. Плейсхолдер выше по разметке, но он
`absolute`, а позиционированные элементы рисуются поверх обычного потока —
пока `<img>` стояла прозрачной, это было не видно, теперь бы размытый слой
лёг поверх чёткой картинки.

#### Результат

Обе точки сняты **на одном хосте** — `dev.uhti.kz/catalog/boys`, одним и тем же
скриптом, 390px, Slow 4G (1.6 Мбит/с, RTT 150 мс), CPU ×4. «До» — сборка
`14f3553`, «после» — `8f9a6f8`. В скобках разброс по прогонам.

|       | прогонов | LCP                      | картинка готова | разрыв LCP−картинка    |
| ----- | -------- | ------------------------ | --------------- | ---------------------- |
| до    | 3        | 13056 мс (10352–15984)   | 9851 мс         | **4185 мс** (610–6133) |
| после | 11       | **5680 мс** (4220–12576) | 4725 мс         | **480 мс** (58–1582)   |

**LCP быстрее на 56%.** TTFB на обеих сборках одинаковый, 475–532 мс, так что
разница целиком в отрисовке, а не в сервере.

Разрыв — главная цифра и главное доказательство механизма: метрика больше не
ждёт гидратации, а срабатывает следом за картинкой. Единственный выброс
«после» (12576 мс) устроен показательно: разрыв в нём 58 мс, то есть тормозила
сама сеть на картинке, а не JS. Раньше так вело себя только одно измерение
из трёх, теперь — все.

Оговорка честная: «до» осталось всего три прогона. Добрать их уже нельзя,
превью пересобрано, а вернуть старую сборку ради статистики не стоит.

Проверено глазами: карточка на 390 и 1440 попиксельно та же, главная и
карточка товара без ошибок в консоли.

#### Найдено следом: сетка терялась в трети рендеров

Обнаружено 15 августа при попытке взяться за `modulepreload`, закрыто веткой
`fix/catalog-ssr-flaky`.

Замеры LCP разлетались от 4.5 до 31 секунды, и списать это на нагрузку машины
не вышло: разброс воспроизвёлся и на превью. Причина оказалась в том, что
**категория через раз отдавалась вообще без сетки**:

```
локальная сборка   с сеткой  3 из 12
превью (UA Googlebot)         8 из 12
```

Товары при этом лежали в payload — то есть `useAsyncData` отрабатывал, а до
разметки данные не доходили.

**Ключ кеша менялся между посевом и отрисовкой.** В `catalogFilters` входят
`priceMin`/`priceMax`, а диапазон цен категории грузится асинхронно
(`loadFilters` → `fetchPriceRangeForCategory`) уже ПОСЛЕ того, как
`useCatalogQuery` посеял кеш. До ответа в фильтре стоит заглушка `[0, 50000]`,
после — реальные границы (`[490, 89900]` у `boys`). `useQuery` при отрисовке
читает данные по новому ключу, не находит и отдаёт скелетоны. Успевал ли
диапазон прийти до конца рендера — от прогона к прогону по-разному, отсюда и
«через раз».

Хуже всего то, что пустой рендер попадал в SWR-кеш маршрута (`/catalog`,
30 минут) и раздавался оттуда всем, включая поискового робота.

Правка: цена и число деталей попадают в фильтр только когда пользователь
реально сузил диапазон. Сравнение с самим диапазоном устойчиво в обоих
состояниях — до загрузки значение равно заглушке диапазона, после равно
реальным границам, — поэтому ключ один и тот же. Логика вынесена в
`utils/catalogFilterRange.ts`, 4 теста.

Результат:

|                      | до правки | после        |
| -------------------- | --------- | ------------ |
| локальная сборка     | 3 из 12   | **15 из 15** |
| превью, UA Googlebot | 8 из 12   | **12 из 12** |

Замер на превью снимался с привязкой к `buildId`: первая попытка дала 9 из 12
и выглядела как «правка не помогла», но пришлась на выкатку — часть ответов
отдавала ещё старая сборка. С фиксацией сборки пустых рендеров не осталось.

#### Что осталось из старых рычагов

Они по-прежнему верны, просто больше не первоочередные. Актуальные цифры
на 15 августа: payload **278 КБ** (был 507), `modulepreload` в голове **41**
штука, крупнейший чанк 273 КБ докачивается к 8.6 с. Опыт с вырезанием
`modulepreload` на лету дал HTML к 3.8 с вместо 9.8 с, но LCP не сдвинул —
до этой правки его держала прозрачность, а не канал. Стоит перемерить теперь.

#### История: сетка не рендерилась на сервере

Трасса на превью (390px, Slow 4G, CPU ×4) до правки:

```
TTFB          480 мс   сервер быстрый
FCP          4424 мс   первым красится фильтр-чип, не товары
JS 273 КБ    3245 мс + 3164 мс на скачивание и разбор
RPC старт    7931 мс   get_filtered_products уходит только теперь
товары      ~9980 мс
картинки    10358 мс
LCP         12044 мс   картинка товара
```

Название LCP-товара встречалось в HTML шесть раз и **ни разу вне `<script>`** —
только в payload. Карточек в разметке 0, скелетонов 68.

Причин было две, обе сняты коммитом `e8b8541`:

1. **SSR-префетч в `useCatalogQuery` не работал.** Стоял `useAsyncData` без
   `await`, а `ssrData.value` читался следующей строкой — синхронно, до
   разрешения промиса. `setQueryData` не вызывался ни разу.
2. **Сетка лежала под `<ClientOnly>`** с `ProductGridSkeleton` в `#fallback`.

Порядок вызовов в композабле принципиален, оба неверных варианта проверены
запуском:

- `await` перед `useQuery` роняет страницу в 500: внутри вызывается
  `useQueryClient()`, а после ожидания контекст инъекции потерян;
- посев кеша **после** `useQuery` не даёт ничего: на сервере vue-query
  не подписывает наблюдателя на кеш.

Рабочий порядок: клиент берём синхронно, ждём данные, сеем кеш, затем создаём
`useQuery` с явно переданным `queryClient`.

Результат на превью: карточек в разметке 0 → **12**, `<img>` 8 → **33**,
гидратация без предупреждений на 390px и 1440px, CLS категории 0.0004.
Для краулера это полноценная страница вместо скелетонов.

#### Почему LCP тогда не улучшился — и почему объяснение было неверным

Ниже разбор от 14 августа. Он верен по цифрам, но **вывод из него был сделан
неправильный**: канал назначили виновником, потому что разрыв между готовой
картинкой и LCP объяснить было нечем. Настоящая причина — `opacity: 0` на
самой картинке (см. начало пункта). Текст оставлен как есть: сами замеры
пригодны, ошибочна только их трактовка.

**12.0 → 11.5 с, то есть в пределах шума.** Картинки стали стартовать раньше
(7.7 с вместо 10.3 с), но выигрыш съеден тем, что сама разметка приходит
только к 7.6 с. Замер после правки:

```
HTML полностью получен  7665 мс
скрипты стартуют        3859 мс  — больше 20 файлов параллельно
самый крупный чанк      273 КБ, докачивается к 8272 мс
```

Дело не в весе разметки: сжатой она 182 КБ, это меньше секунды на Slow 4G.
Дело в том, что на 3.9-й секунде браузер находит в `<head>` два десятка
`modulepreload` и они забирают канал ровно тогда, когда нужен HTML.

Вторая цифра в ту же сторону: из 691 КБ несжатого HTML **507 КБ — это payload
Nuxt**, а собственно разметки 159 КБ. Данные каталога уезжают дважды —
в разметке и в payload.

#### Рычаги на следующий заход

1. **Урезать payload.** 507 КБ на страницу — данные, которые уже есть
   в разметке. Самый весомый рычаг из трёх.
2. **Проредить `modulepreload`.** Два десятка файлов в голове забивают канал
   в самый неподходящий момент.
3. **Preload LCP-картинки**, чтобы первая карточка не ждала конца разметки.

### CLS главной: причина и правка

Закрыто коммитом `87f28b4`. Разбор стоит того, чтобы остаться в документе:
похожая конструкция есть и на других страницах.

Замер на превью (390px, Slow 4G, CPU ×4, атрибуция через `PerformanceObserver`)
показал: сдвигов четыре, но два дают 0.2427 из 0.244. Двигался один блок —
«Популярные категории»:

```
4964 мс  y=1213        скелетон держит место
5739 мс  y= 707  -506  скелетон снят, на его месте пусто
6574 мс  y=1225  +518  карусель наконец отрисовалась
```

Дёргал **не** переход «скелетон → карусель», а дыра между ними. Скелетон
снимался условием `!shouldRenderLowerBlocks`, а это не состояние загрузки,
а `setTimeout` на 1000 мс (`pages/index.vue`). Карусели ленивые
(`defineAsyncComponent`), и к моменту снятия скелетона их чанк ещё грузился —
блок схлопывался на ~800 мс и разворачивался обратно. Промежуток между
сдвигами, 835 мс, ровно об этом.

Теперь скелетон снимается по `@vue:mounted` самой карусели, а не по таймеру.

Проверено одним и тем же трейсом на локальной сборке, до и после:
без правки CLS 0.3119 со скачком −506, с правкой 0.1921 и скачка нет
(заголовок смещается на +12). Остаток 0.19 — локальный артефакт: бакеты
storage на локальной базе пусты, картинки не приходят, высоты плывут.
На превью этого нет.

**Не проверено:** цифра на превью. Сборка `87f28b4` на момент написания
не выкачена — check-suite Vercel завис в статусе `queued`, при том что
GitHub событие доставил, проект не на паузе, лимиты не исчерпаны и
инцидентов на платформе нет. Перемерять после выкатки.

### Не является багом

- **`Clean-param: brands` в robots против `?brand=` в URL.** Параметров действительно два: `brands` — мультифильтр (`[...slug].vue:954`), `brand` — SEO-лендинги категория+бренд (строка 951). Первый чистится, второй намеренно оставлен индексируемым. Проверено, всё верно.

- **Концевые числа в названиях товаров.** Выглядят огрызками, но 17 из 24 — модели и артикулы (Ferrari 488, MOKA 2075, Mermaze 580812), по которым ищут. Правило по их отбрасыванию рассматривалось и отклонено.

  с самым большим текстом (2196 знаков) стоит на 43-й позиции.
- **«У запросов на позициях 4–10 плохие сниппеты».** Не подтверждено:
  4–15 показов слишком мало для вывода, а низкий CTR на позициях 6–10 —
  норма. Исключение одно и оно исправлено — брендовый запрос «uhti».
- **«CLS категории 0.090 — настоящий сдвиг вёрстки».** Не подтверждено
  ни в одном прогоне реального браузера. Разбор — ниже отдельным разделом.

### CLS категории 0.090: воспроизвести не удалось

Lighthouse стабильно показывает 0.090 и относит 0.0881 к контейнеру
`div > div.flex > main.flex-1 > div.w-full`, а 0.0020 — к `button.cf-chip`.
В реальном браузере при условиях **строго жёстче** лабораторных сдвига нет:

| условия прогона                        | CLS        |
| -------------------------------------- | ---------- |
| без троттлинга                         | **0.0000** |
| Slow-4G + CPU ×4 (профиль Lighthouse)  | 0.0004     |
| Slow-4G + CPU ×10                      | 0.0004     |

Единственный настоящий сдвиг — 0.0004 на `button.cmh-icon-btn`: в шапке
после гидратации появляется вторая иконка. Это видно и на плёнке PSI между
кадрами 3797 и 4430 мс.

Проверены и отброшены четыре механизма:

- **FOUC — стили не применены к первой отрисовке.** Опровергнуто. Все 7
  таблиц блокирующие и лежат в `<head>` до инлайнового блока; они
  завершаются на 3881 мс, FCP — 3976 мс, то есть отрисовка честно их ждёт.
  Раннее наблюдение «`hidden lg:block` занимает 363 px» оказалось
  **артефактом моего же замера**: `getBoundingClientRect()` в polling'е
  форсирует layout при ещё не загруженных таблицах, и геометрия, которую я
  видел, на экран никогда не попадала.
- **Цена и кнопка «+» доезжают в карточку после гидратации.** Опровергнуто:
  у `ClientOnly` есть `#fallback` с той же высотой `h-[52px]`, а
  кросс-корреляция кадров плёнки даёт **0 px** смещения между всеми
  кадрами после первой отрисовки.
- **Поздний CSS страницы меняет геометрию над сгибом.** CSS страницы и
  фильтров правда не блокирующий (`_slug_.css` доезжает на 4672 мс против
  FCP 3976 мс), но блокировка всех шести таких таблиц меняет только общую
  высоту документа на 32 px ниже сгиба; ряд чипов в обоих случаях `y282 h38`.
- **Определение устройства по User-Agent отдаёт Lighthouse десктопную
  разметку.** Опровергнуто: серверной UA-логики в проекте нет, все
  `isMobile` считаются на клиенте через `window.innerWidth` и `useMediaQuery`.

Вывод: цифра лабораторная. Локальный Lighthouse в WSL поднять не удалось
(`NO_FCP`, затем `ERR_ABORTED`), поэтому докопаться до причины именно
лабораторного значения нечем. Полевых данных по домену нет (см. CrUX ниже),
так что практического веса у этой цифры сейчас тоже нет.

### Почему категории стоят на 22–39

Разобрано по запросам: страницы показываются по **широким однословным**
запросам национального масштаба, где в выдаче маркетплейсы.

```
/catalog/constructors-root/konstruktory-malchikam
  поз 76.7 | «конструктор»       ← широкий запрос
  поз  9.0 | «конструкторы»      ← чуть уже, и сразу топ-10
/catalog/girls/kukly/kukly-lol
  поз 39.2 | «кукла l.o.l.»
  поз 48.3 | «кукла лол»
```

Разница между «конструктор» (76-я) и «конструкторы» (9-я) — 67 позиций на
одном слове. Технически с категориями всё в порядке: в индексе, SSR-разметка
полная, canonical корректный, скорость улучшена, гидратация чистая. Низкие
позиции — это конкуренция, а не дефект. **Рычага в коде здесь нет:** влияют
ассортимент, внешние ссылки и охват длинного хвоста.

### Про методику замера

Медиана считается по трём прогонам с паузой 90 секунд между кругами. Пауза
принципиальна: 14 августа при паузе в 2 секунды PSI отдавал кеш, и «медиана
пяти прогонов» выходила из пяти одинаковых значений — `[77,77,77,77,77]`,
`[50,50,50,50,50]`. Теперь разброс настоящий и виден в отдельном столбце:
у главной на мобиле 56–75, у категории на десктопе 76–90. Девятнадцать баллов
разброса — это и есть цена одиночного прогона.

**Главное достижение — LCP категории: 8.7 → 4.7 с.** Это результат SSR-сетки

**CLS главной 0.249 → 0.000** — правка `87f28b4`, скелетон ленты держится

### Что осталось плохим

**Speed Index категории — 7.8 с.** Худшая метрика сайта. При LCP 4.7 это
значит, что главный элемент появляется вовремя, а страница ещё долго

**TBT главной вырос: 240 → 287 мс.** Единственная метрика, которая

нельзя, но приглядеться стоит.

### Найдено при разборе Speed Index: половину документа весили подложки

Разбор состава документа дал находку крупнее самого Speed Index.
**data:URI занимали 50–56% сжатого веса КАЖДОЙ страницы:**

| страница        | brotli было | без data:URI | доля     |
| --------------- | ----------- | ------------ | -------- |
| `/catalog/boys` | 78.5 КБ     | 39.2 КБ      | **50%**  |
| `/`             | 55.9 КБ     | 24.6 КБ      | **56%**  |
| `/catalog`      | 53.9 КБ     | 24.3 КБ      | **55%**  |

Больше половины этого — LQIP-подложки всех 51 категории с картинкой: общая
выборка категорий тащила их на каждую страницу сайта. На `/catalog/boys` в
документе было 86 data:URI при 33 `<img>` в разметке.

В первой отрисовке подложки категорий не участвуют **нигде**: сетка
`/catalog` рисует картинки внутри `ClientOnly` и только при `!isMobile`,
`HomePopularCategories` монтируется по `requestIdleCallback`, а
`components/category/CategoryDescription.vue` — третий читатель поля — не
подключён ни на одной странице. Поэтому подложки убраны из общей выборки и
догружаются на клиенте теми, кто их рисует (`6b8b80e`).

Проверено на локальной сборке: ни одной из 51 подложки (70.7 КБ) ни в одном
документе; `/catalog` на 1440px — 27 карточек из 29 с LQIP (столько их с
картинкой); на 412px картинок категорий нет и запрос подложек не уходит;
главная — 18 плиток с LQIP после idle.

Что осталось из той же области: на `/catalog/boys` живыми остаются 34
data:URI на 38.9 КБ — это подложки товаров, и они честно используются в
SSR-сетке. Медиана одной подложки 1.4 КБ; типичный LQIP укладывается в
300–600 байт, так что здесь есть ещё кратный запас — но он требует
перегенерации подложек в базе, то есть записи в прод.

### Побочная находка: мёртвый компонент

`components/category/CategoryDescription.vue` не подключён ни на одной
странице. Совпадения в поиске — одноимённые функции
`generateCategoryDescription` и `generateBrandCategoryDescription` в
`pages/catalog/[...slug].vue`. Не удалён: по правилам проекта чистка
мёртвого кода идёт отдельной `refactor/*`, а не попутно.

## Как повторить замеры

Настройка окружения (Python-рантайм, Chromium, ключ Google) — в [CLAUDE_SETUP.md](./CLAUDE_SETUP.md).

Те же три URL, что и 13 августа:

```bash
claude-seo run pagespeed_check.py https://dev.uhti.kz/ --strategy both --json
claude-seo run pagespeed_check.py https://dev.uhti.kz/catalog/boys --strategy both --json
claude-seo run pagespeed_check.py https://dev.uhti.kz/catalog/products/akkordeon-detskiy-hih02-plastik-zvukovye-effekty-yarkiy-dizayn-dlya-detey-ot-3-let --strategy both --json

# только полевые данные
claude-seo run pagespeed_check.py https://uhti.kz/ --crux-only --json

# разбор одной страницы
claude-seo run parse_html.py --url https://dev.uhti.kz/ --json
```

Нужные поля в JSON лежат в `psi.mobile.lighthouse_scores`, `psi.mobile.lab_metrics`, а консольные ошибки — в `psi.mobile.audit_details["errors-in-console"].items`.

**Между повторными прогонами одного URL нужна пауза в минуты, а не в секунды.**
При паузе 2 секунды PSI отдаёт кеш, и медиана считается по одному и тому же
значению — 14 августа так и вышло, `[77,77,77,77,77]`. На 90 секундах разброс
становится настоящим: 56–75 у главной на мобиле.

### Search Console

```bash
# какие ресурсы доступны и с каким уровнем прав
claude-seo run gsc_query.py sites

# запросы и позиции; --dimensions принимает query, page или пару через запятую
claude-seo run gsc_query.py query --days 28 --dimensions query --limit 500 --json
claude-seo run gsc_query.py query --days 28 --dimensions query,page --limit 1000 --json

# состояние sitemap глазами Google
claude-seo run gsc_query.py sitemaps

# индексация одного адреса
claude-seo run gsc_inspect.py "https://uhti.kz/catalog/boys"
```

Инспекция всех адресов делалась разовым скриптом на venv плагина: взять `<loc>`
из sitemap прода, ходить пулом из 6 потоков в `urlInspection().index().inspect()`
с `siteUrl: 'sc-domain:uhti.kz'`. Квота — 2000 запросов в сутки, 600 в минуту,
на 309 адресах ушло около шести минут.

Граф внутренних ссылок (для поиска сиротских страниц) считался обходом всех
адресов sitemap с выборкой `<a href>` из разметки **после удаления
`<script>`** — иначе в подсчёт попадают ссылки из payload, которых робот
не видит. Важно: `/brands` в sitemap до 17 августа не входил, и его отсутствие
в списке адресов дало ложный вывод о сиротстве.

Обход всего sitemap с подсчётом мета-тегов и заголовков делался разовым скриптом на venv плагина (`~/.local/share/claude-seo/.venv/bin/python`, там есть `requests`, `bs4`, `lxml`). Суть: забрать `<loc>` из `https://dev.uhti.kz/sitemap.xml`, подменить хост на превью (в sitemap лежат канонические адреса `uhti.kz`), обойти пулом в 6 потоков с UA Googlebot и посчитать по каждому URL `title`/`description`/число `<h1>`/`canonical`, отдельно помечая описания, попавшие под срез: `re.match(r"^.{50} \(", desc)`.
